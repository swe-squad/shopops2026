## Accepted product policy

- Each registered **user** owns an isolated team: one orchestrator plus 2–3 specialists. Shop ownership is an authorization dimension, not the provisioning key.
- Shared Data and Knowledge–Memory services authorize identity and shop/product scope on every applicable query. Instructions and sandbox separation cannot replace service authorization.
- Archive conversations after 10 minutes of application inactivity. This is ShopOps policy, distinct from turn completion, provider retention and sandbox expiry.
- Existing `services/agent-core/agents_api_template_requirements.md` assumes one orchestrator per shop; this conflicts with the accepted user-owned team and needs correction in the owning product documentation.

## Verified provider contract and implications

**Runtime.** Agents API supplies an OpenAI-managed Codex harness, including orchestration, context compaction and recovery. Agents SDK runs its loop in the application instead; these are different deployment choices. Choose Agents API for the requested managed runtime. [Official runtime comparison](https://developers.openai.com/api/docs/guides/agents).

**Session and identity.** Agent configuration, optional environment, durable session and event/item history are separate concepts. OpenAI-hosted mode lets the application submit tasks and receive results while OpenAI operates compute. The provider does not provision ShopOps users or authorize shop membership: backend storage must map authenticated user → team/configuration → application conversation → provider session/environment. No provider-created per-user assignment was established. Agents API currently retains session state, supports US data residency only, and is not ZDR eligible. [Agents API overview](https://developers.openai.com/api/docs/guides/agents-api/overview).

**Sandbox isolation.** Each hosted session has a separate workspace. Files persist across turns while its sandbox exists; templates reuse configuration, not a running workspace. Therefore per-user isolation requires preventing another user from receiving/reusing that user's session or environment. Separate conversations may have separate hosted workspaces; do not promise a permanent dedicated machine per registered user. Activity and keep-alives stopping for an hour can allow deletion; timeout is nonconfigurable. Published output artifacts can remain downloadable after sandbox expiry. [OpenAI-hosted sandboxes](https://developers.openai.com/api/docs/guides/agents-api/environments/openai-hosted).

**Team.** Enable `agent.multi_agent.enabled`; set `max_concurrent_subagents` to 2 or 3. This is a concurrency ceiling excluding the coordinator, not a guarantee that exactly that many persistent named specialists always exist. Harness supplies create/message/wait/interrupt actions. Coordinator and subagents share the session filesystem; spawning does not allocate another environment. Subagents inherit MCP tools, credentials and allowed tools; they do not support function tools. Product roles and dispatch policy must supply the intended specialist responsibilities. Their shared credentials make MCP authorization essential. [Multi-agent guide](https://developers.openai.com/api/docs/guides/agents-api/multi-agent).

**Turn completion.** Input to an idle session starts a turn; input during work steers the active turn. Track completed/failed/cancelled events and inspect output; idle alone does not prove success. Stream closure does not cancel work. Save message idempotency keys and reconcile saved session items after disconnects. [Run and continue sessions](https://developers.openai.com/api/docs/guides/agents-api/sessions).

**10-minute archive.** Maintain application `last_activity_at` and archived state. Before archiving, reconcile incoming input and active/required-action work; avoid treating lack of a Telegram message as successful task completion. Archive preserves application history and any retained provider mapping. Provider deletion removes the API session and requests asynchronous cleanup; cancellation stops current work while retaining conversation. No archive operation or configurable ten-minute sandbox timeout was established. If cost cleanup later requires deletion, persist approved history/artifacts first and start a new mapped session on return. [Manage sessions](https://developers.openai.com/api/docs/guides/agents-api/sessions/manage).

**MCP route.** HTTP `connection_origin: service` is default and requires a server reachable from OpenAI; `environment` connects from the session environment. Session HTTP credentials/custom headers can be set with `transport.authorization`/`transport.headers`; API encrypts and omits these from returned session data. Vault-backed auth applies to OpenAI-origin connections. Use `allowed_tools` and `required` for tool discovery/startup policy. Private CapRover DNS is not automatically reachable from OpenAI-hosted compute: expose the intended HTTPS MCP boundary or deploy a trusted reachable bridge. A private `srv-captain--...` URL remains valid only for callers actually on that cluster network. [MCP connections](https://developers.openai.com/api/docs/guides/agents-api/tools/mcp).

## PR #3: actual current Data MCP design

The PR body describes an older RS256/JWKS design and interval-based `mart_ready` completion. Current source and handoff supersede those descriptions. Treat the body as stale; do not copy it as current integration authority. [PR #3](https://github.com/swe-squad/shopops2026/pull/3).

- **Current identity:** `X-Phone-Number`, canonical international format; no JWT, OTP or proof of ownership. Knowledge of the number grants access. Each request rechecks live authoritative `access.user_shop_access`; configured shops intersect membership. `list_shops` returns allowed shops; data tools select `shop_key`. Server configuration provides capability scopes. This identifies a caller under the accepted prototype rule; it is not verified authentication. [Pinned auth implementation](https://github.com/swe-squad/shopops2026/blob/3ec1107eec4bf4284a3a17f8cee5d799e6520883/services/shop-data-mcp/app/auth.py).
- **Tool surface:** `list_shops`, `search_catalog`, `describe_dataset`, `query_mart`, raw-access request/query, expiring private temp marts, bounded result reads, refresh and operation polling. Catalog metadata explains grain/fields/freshness. Queries run through restricted shop database access; saved results and source grants are rechecked. Product-specific authorization is not represented in the inspected principal/catalog selection: keep query-level product scope as required integration work, not implemented evidence. [Pinned tools](https://github.com/swe-squad/shopops2026/blob/3ec1107eec4bf4284a3a17f8cee5d799e6520883/services/shop-data-mcp/app/server.py), [service scope enforcement](https://github.com/swe-squad/shopops2026/blob/3ec1107eec4bf4284a3a17f8cee5d799e6520883/services/shop-data-mcp/app/service.py).
- **Approval:** requesting raw access never grants it. External verified-owner flow supplies subject/shop-bound grants for fields and time range with expiry/revocation. Missing integrations fail closed. [Pinned handoff](https://github.com/swe-squad/shopops2026/blob/3ec1107eec4bf4284a3a17f8cee5d799e6520883/services/shop-data-mcp/HANDOFF.md).
- **Refresh now:** implemented PR #6 bridge refreshes the full source snapshot using `resource=snapshot`; finishes `snapshot_ready`, `refresh_mode=full_snapshot`, `applied_source_revision`, `coverage=null`. Requested time bounds are policy/audit context, not a historical backfill filter. Never describe this as interval-complete `mart_ready`; that remains a future contract. [Pinned integration](https://github.com/swe-squad/shopops2026/blob/3ec1107eec4bf4284a3a17f8cee5d799e6520883/services/shop-data-mcp/INTEGRATION.md).

## Integration limits / unresolved questions

- Live Agents API account access, exact SDK version, deployment, real MCP connection, actual memberships/catalog/DB roles and operational data remain unverified by this research.
- Keep phone-only identity as the current prototype decision; do not silently replace it with JWT/OTP. A production authenticated-user boundary remains a separate explicit product decision.
- Specify enforced product permission representation and its propagation through marts, raw grants, temporary results and knowledge/history queries.
- Define which activity resets the ten-minute timer, handling of active turns/approvals, and whether archived sessions are reused or replaced. None changes provider turn/expiry semantics.
- Owner-approval callback/delivery and retention/freshness behavior need integration agreement. Do not advertise future interval collection as the implemented snapshot bridge.
- Docs impact: minor; correct user-vs-shop provisioning, session/archive terminology and current Data MCP identity/refresh contracts in the smallest owning product document.
